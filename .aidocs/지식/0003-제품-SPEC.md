# KNOW-0003 제품 SPEC

## 상태

구현 기준 v0.1

## 제품 목표

AI와 사람이 함께 사용하는 diagram-as-code 편집기를 만든다. 사용자는 텍스트 DSL로 다이어그램을 작성하고, 앱은 이를 실시간으로 렌더링하며, 여러 사용자가 같은 diagram source를 동시에 편집할 수 있어야 한다.

초기 dialect는 Mermaid다. 다만 제품 구조는 Mermaid 전용이 아니라 Mermaid, D2, PlantUML, Graphviz, Structurizr 같은 diagram dialect를 추가할 수 있게 설계한다.

## 사용자

- 개발자: 설계, API 흐름, 시스템 의존성을 빠르게 문서화한다.
- 아키텍트: C4, 컴포넌트, 배포 흐름 같은 구조도를 관리한다.
- 기획/운영 사용자: 복잡한 업무 흐름을 다이어그램으로 정리한다.
- AI 에이전트: 자연어, 코드, 오류 메시지를 바탕으로 다이어그램 source를 생성/수정한다.

## 제품 모드

제품은 하나의 editor core를 공유하되 실행 모드를 분리한다.

### Embedded Editor Mode

외부 사이트에 diagram 편집기만 제공하는 모드다. 파일 탐색기와 자체 스토리지를 노출하지 않고 `value`, `onChange`, `dialect`, `readonly`, `toolbar` 같은 API로 host application이 source와 저장을 제어한다.

용도:

- CMS, 문서 서비스, 내부 admin에 단일 diagram editor 삽입
- 특정 Markdown block이나 DB field를 편집하는 경량 편집기
- 협업 없이 단일 사용자가 source와 preview를 수정하는 화면

### Workspace Editor Mode

사용자가 스토리지 경로를 지정하거나 서버가 workspace root를 제공하면 하위 폴더의 diagram 관련 파일을 목록화하는 IDE형 모드다.

기본 동작:

- 관련 확장자만 파일 트리에 표시한다.
- 사용자는 storage root를 입력하거나 provider가 제공하는 root를 선택한다.
- 좌측 패널은 folder/file tree다.
- 사용자는 마우스 클릭, 위/아래 키, 화살표 버튼, 이전/다음 버튼으로 파일을 순회한다.
- 선택된 파일은 우측 넓은 작업 패널에서 열린다.
- 작업 패널은 editor, preview, split view를 제공한다.
- 큰 다이어그램은 이동 모드, zoom, fit-to-screen으로 탐색한다.
- 우측 도구 패널은 아이콘 기반 tool palette를 제공한다.
- tool palette 항목은 drag/drop 또는 클릭으로 source snippet을 삽입한다.

대상 확장자:

- `.mmd`
- `.mermaid`
- `.md`
- `.mdx`
- `.d2`
- `.puml`
- `.plantuml`
- `.dot`
- `.gv`
- `.structurizr`
- `.dbml`

### Server Collaboration Mode

서버가 웹 편집기를 띄우면서 특정 workspace, 파일, diagram 영역을 launch context로 전달하는 모드다. 사용자는 URL이나 host page에서 바로 지정된 diagram 영역을 보고 동시에 편집한다.

이 모드는 Workspace Editor Mode의 확장이다. 차이는 사용자가 직접 경로를 입력하는 대신 서버가 접근 가능한 storage provider와 diagram target을 결정한다는 점이다.

예시:

- 서버가 `/docs/architecture.md`의 두 번째 `mermaid` code block을 자동으로 연다.
- 서버가 `/diagrams/payment-flow.mmd` 파일을 열고 같은 room의 사용자들을 연결한다.
- 외부 시스템이 특정 diagram id를 넘기고 편집기는 해당 diagram source만 표시한다.

## 핵심 사용 흐름

1. 앱은 실행 모드와 launch context를 해석한다.
2. Embedded mode는 전달받은 source를 바로 editor core에 연결한다.
3. Workspace mode는 storage provider에서 관련 파일 목록을 가져와 좌측 tree를 만든다.
4. 사용자는 파일 tree, 화살표, 위/아래 키, 마우스 클릭으로 diagram target을 선택한다.
5. 선택된 source는 editor와 preview가 결합된 우측 작업 패널에 열린다.
6. 사용자가 source를 편집하면 preview가 debounce 후 SVG로 갱신된다.
7. 렌더링 오류가 있으면 위치와 메시지를 보여준다.
8. 큰 diagram은 pan/zoom/fit-to-screen으로 이동한다.
9. 도구 패널의 아이콘을 클릭하거나 drag/drop하면 dialect별 snippet이 source에 삽입된다.
10. 협업 room에서는 같은 diagram target을 여는 사용자들의 변경, 커서, 선택 영역이 실시간으로 표시된다.
11. AI 보조 기능은 source를 직접 덮어쓰지 않고 proposal/diff로 제안한다.

## MVP 범위

MVP는 단일 앱 화면에서 Mermaid source를 작성하고 즉시 미리보는 기능을 완성한다. 동시에 협업 확장을 막지 않도록 source 상태와 renderer를 분리한다.

MVP에 포함한다.

- Vite, React, TypeScript 앱
- CodeMirror 기반 source editor
- Mermaid dialect adapter
- 실시간 SVG preview
- 렌더링 상태 표시: `idle`, `rendering`, `success`, `error`
- syntax/render error panel
- Mermaid 템플릿 선택
- SVG export
- Markdown fenced code block import/export
- Embedded Editor Mode
- Workspace Editor Mode의 기본 shell
- 파일 tree와 파일 선택 상태
- preview pan/zoom/fit-to-screen
- 아이콘 기반 tool palette
- 기본 테스트와 수동 검증 문서

협업 MVP에 포함한다.

- Yjs `Y.Text('source')` 기반 source 동기화
- Hocuspocus WebSocket room
- server launch context 기반 diagram target 자동 열기
- 접속자 목록, remote cursor, selection
- Yjs awareness 기반 presence
- 서버 persistence
- 브라우저 IndexedDB cache

MVP에서 제외한다.

- 직접 노드를 드래그하는 WYSIWYG 편집
- 모든 Mermaid 문법별 전용 폼 편집기
- PlantUML, D2, Graphviz 렌더링 구현
- 세밀한 조직/팀 권한 관리
- 결제, 계정 초대, 관리자 콘솔
- 이미지에서 diagram source를 추출하는 기능
- 임의 서버 경로에 대한 무제한 브라우저 접근

## 데이터 모델

초기 클라이언트 모델은 다음 구조를 기준으로 한다.

```ts
type EditorMode = 'embedded' | 'workspace' | 'collaboration';

type DiagramDialectId =
  | 'mermaid'
  | 'd2'
  | 'plantuml'
  | 'graphviz'
  | 'structurizr';

type DiagramDocumentMeta = {
  id: string;
  title: string;
  dialect: DiagramDialectId;
  createdAt: string;
  updatedAt: string;
};

type DiagramTarget =
  | {
      kind: 'file';
      uri: string;
      dialect: DiagramDialectId;
    }
  | {
      kind: 'markdown-block';
      uri: string;
      dialect: DiagramDialectId;
      blockIndex: number;
      startLine: number;
      endLine: number;
      sourceHash: string;
    };

type LaunchContext = {
  mode: EditorMode;
  workspaceId?: string;
  rootUri?: string;
  target?: DiagramTarget;
  roomId?: string;
  readOnly?: boolean;
};

type RenderState =
  | { status: 'idle' }
  | { status: 'rendering' }
  | { status: 'success'; svg: string }
  | { status: 'error'; message: string; line?: number; column?: number };
```

Storage provider는 모드별 저장소를 같은 방식으로 다루기 위한 인터페이스다.

```ts
type DiagramFile = {
  uri: string;
  name: string;
  relativePath: string;
  dialectHint?: DiagramDialectId;
  kind: 'file';
};

type StorageProvider = {
  id: string;
  listFiles: (rootUri: string) => Promise<DiagramFile[]>;
  readTarget: (target: DiagramTarget) => Promise<string>;
  writeTarget: (target: DiagramTarget, source: string) => Promise<void>;
  watch?: (rootUri: string, onChange: () => void) => () => void;
};
```

협업 문서는 다음 Yjs shared type을 기준으로 한다.

```ts
const ydoc = new Y.Doc();
const source = ydoc.getText('source');
const meta = ydoc.getMap('meta');
const settings = ydoc.getMap('settings');
```

저장 대상과 파생 대상을 분리한다.

| 대상 | 저장 방식 |
| --- | --- |
| source | `Y.Text` 또는 일반 string |
| title, dialect, settings | `Y.Map` 또는 DB metadata |
| cursor, selection, users | awareness, 영구 저장 안 함 |
| preview SVG | source에서 파생, 영구 저장 안 함 |
| diagnostics | source에서 파생, 영구 저장 안 함 |

## 협업 기준

협업은 storage 입력의 확장으로 본다. 사용자가 직접 storage root를 고르는 대신 서버가 `LaunchContext`를 전달하면 편집기는 해당 context의 diagram target을 자동으로 연다.

기준:

- 협업 room의 단위는 `DiagramTarget`이다.
- 기본 room id는 `workspaceId + target.uri + target.kind + blockIndex`에서 결정한다.
- `.mmd`, `.mermaid`, `.d2`, `.puml`처럼 파일 전체가 diagram인 경우 파일 전체 source를 공유한다.
- `.md`, `.mdx`처럼 여러 diagram block을 포함할 수 있는 경우 특정 fenced code block만 `DiagramTarget`으로 공유한다.
- 하나의 room은 하나의 `Y.Doc`를 가진다.
- `Y.Text('source')`는 해당 target의 diagram source만 담는다.
- 서버는 room 최초 생성 시 storage provider에서 source를 읽어 Yjs document를 seed한다.
- 서버는 Yjs update를 저장하고, 필요 시 target source를 원래 storage에 다시 쓴다.
- cursor, selection, 접속자, viewport 상태는 awareness로만 동기화한다.
- preview SVG와 diagnostics는 각 client가 source에서 다시 계산한다.
- 서버 launch context로 열린 사용자는 client에서 임의 경로를 직접 선택할 수 없다.
- storage의 원본 파일이 외부에서 바뀐 경우 `sourceHash`나 version을 비교해 stale 상태로 표시한다.

서버 launch 예시는 다음과 같다.

```ts
const launchContext: LaunchContext = {
  mode: 'collaboration',
  workspaceId: 'docs-main',
  rootUri: 'server://workspace/docs',
  target: {
    kind: 'markdown-block',
    uri: 'server://workspace/docs/architecture.md',
    dialect: 'mermaid',
    blockIndex: 1,
    startLine: 42,
    endLine: 68,
    sourceHash: 'sha256:...'
  },
  roomId: 'docs-main:architecture.md:mermaid:1'
};
```

## Dialect Adapter

모든 renderer는 같은 인터페이스로 연결한다.

```ts
type Diagnostic = {
  severity: 'error' | 'warning' | 'info';
  message: string;
  line?: number;
  column?: number;
};

type RenderResult =
  | { ok: true; svg: string }
  | { ok: false; diagnostics: Diagnostic[] };

type DiagramDialect = {
  id: DiagramDialectId;
  label: string;
  detect: (source: string) => boolean;
  render: (source: string) => Promise<RenderResult>;
  validate?: (source: string) => Promise<Diagnostic[]>;
  format?: (source: string) => Promise<string>;
  templates: DiagramTemplate[];
  aiHints: string;
};
```

## UX 원칙

- 첫 화면은 실제 편집 화면이어야 한다.
- 에디터와 뷰어는 같은 문서를 바라보는 하나의 작업면이어야 한다.
- toolbar는 아이콘 중심으로 구성하고 필요한 경우 tooltip을 제공한다.
- 오류는 사용자를 막지 않고 source 수정에 필요한 정보만 보여준다.
- preview가 실패해도 source는 보존한다.
- 협업 상태는 작업을 방해하지 않는 밀도로 표시한다.
- 파일 tree는 탐색 도구이고, 편집의 주체는 항상 선택된 diagram source다.
- tool palette의 시각 조작은 별도 객체 저장이 아니라 source snippet 삽입으로 환원한다.
- pan mode는 preview 이동을 위한 모드이며 source 편집 모드와 명확히 구분한다.

## 검증 기준

- `npm run typecheck` 통과
- `npm run test` 통과
- `node ../osv-check/bin/osv-check.js . -e npm -s HIGH` 통과
- Mermaid flowchart/sequence/class/ERD 예제 렌더 확인
- 잘못된 Mermaid source 입력 시 오류 표시 확인
- SVG export 파일이 유효한 SVG인지 확인
- Workspace mode에서 관련 확장자 파일만 tree에 표시되는지 확인
- 파일 tree에서 마우스와 키보드 순회가 동작하는지 확인
- preview pan/zoom/fit-to-screen이 큰 diagram에서 동작하는지 확인
- 협업 구현 후 두 브라우저 세션에서 동기화 확인
- server launch context로 특정 file 또는 Markdown block이 자동으로 열리는지 확인
- Playwright로 desktop/mobile 레이아웃이 깨지지 않는지 확인

## 초기 구현 결정

2026-05-05 구현 착수 기준으로 다음을 결정한다.

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 첫 배포 형태 | embedded/static SPA 우선 | Mermaid 편집/preview core를 먼저 안정화하고, 협업 서버는 같은 core 위에 확장한다. |
| 인증 범위 | MVP에서는 계정 기반 인증 제외, 협업 단계는 익명 room 우선 | 문서 편집 core와 Yjs 동기화 검증을 먼저 끝낸다. |
| AI 연동 | 로컬 mock proposal 우선 | source를 직접 덮어쓰지 않는 diff/proposal UX를 먼저 검증한다. |
| 첫 workspace provider | browser File System Access API 계열 우선, server provider는 협업 단계에서 추가 | 정적 SPA 배포와 로컬 문서 편집 흐름을 먼저 지원한다. |
| Markdown block target 식별 | explicit id 우선, 없으면 block index + sourceHash fallback | 외부 수정에 강한 식별자를 우선하고, 기존 Markdown도 열 수 있게 한다. |

## 남은 열린 질문

- 협업 서버를 실제 배포할 때 인증/권한 모델을 어디까지 둘지 결정해야 한다.
- browser workspace provider에서 지원하지 않는 브라우저의 fallback UX를 결정해야 한다.
